# Architecture

This is a static, client-only React app. There is no backend and no database — the browser is the whole system. This doc explains how the pieces fit together and *why* they're shaped this way, so a future contributor (including future-you) doesn't have to reverse-engineer it from the code.

## The big picture

```
┌────────────────────┐     ┌─────────────────────────────────────────────┐
│  Template picker    │     │                  Editor                     │
│  (105 live thumbnails────▶│  ┌──────────────┐                          │
│  grouped by layout,  │     │  │ Dock          │──▶ Zustand store        │
│  full page "/" or    │     │  │ (dates, tax,  │    (single Invoice)     │
│  in-editor drawer)   │     │  │  columns,     │         │               │
└────────────────────┘     │  │  sections,    │         ▼               │
                            │  │  design/style)│   ┌────────────────────┐ │
                            │  └──────────────┘   │  InvoicePreview     │ │
                            │                      │  (renders the active│ │
                            │   click any text ───▶│   template, editable│ │
                            │   on the canvas       │   in place, with    │ │
                            │   to edit it in place  │   live store data)  │ │
                            │                      └──────────┬──────────┘ │
                            └───────────────────────────────┼──────────────┘
                                                             │
                                            same DOM node ───┤
                                                             ▼
                                        ┌────────────────────────────────┐
                                        │   Export pipeline (on click)     │
                                        │   image / pdf ← rasterize node   │
                                        └────────────────────────────────┘
```

The one idea that shapes almost every other decision below: **there is exactly one `Invoice` object, held in one store, and the live preview renders it directly.** The image and PDF exporters don't re-render anything — they capture the *same DOM node* that's already on screen. What you see in the editor is, pixel for pixel, what you download. This is the WYSIWYG guarantee, and it's why the app doesn't need a separate "export renderer."

**There is no sidebar.** Editing happens two ways: click directly on any business-info, client-info, line-item, or logo field on the invoice itself to edit it in place (see "Click-to-edit" below), or use the slim top toolbar for the handful of things that have no visual home on the page — invoice #/dates, currency/tax/discount, column visibility, section show/hide, and design/style. It's a page-builder rather than a traditional form-plus-preview editor.

## Data model (`src/types/invoice.ts`)

A single `Invoice` type holds everything: business/client info (`Party`), line items, currency/tax/discount, notes, the selected `templateId`, a `theme` (accent color, font, and page padding), and `sections` (see below). Every template component, every exporter, and the Zustand store all speak this one type — there's no per-template data shape.

### Section visibility (`SectionVisibility`)

Logo, business details, client details, payment terms, bank details, notes, and the signature block are all optional — each has a boolean in `invoice.sections` toggled by a checkbox in the toolbar's Sections popover. Deliberately modeled as explicit flags rather than "render it if the field happens to be non-empty": that would make a field's mere presence its own visibility switch, with no way to keep the text saved but temporarily leave it off an invoice. Every layout is expected to gate these sections on the flag (see `hasFooterContent()` in `src/templates/shared/sectionVisibility.ts`, and [ADDING_A_TEMPLATE.md](./ADDING_A_TEMPLATE.md)) rather than inferring visibility itself, so the checkboxes are a reliable contract across every design, not a per-layout convention.

Line items and the invoice number/dates are *not* in `SectionVisibility` — those aren't optional. Tax and discount aren't either: a hidden tax row that's still folded into the total would make the invoice's displayed math not add up, so those stay tied to their rate being non-zero rather than getting an independent switch. When only one of the "from"/"to" party blocks is visible, layouts render just that one rather than leaving an empty grid cell — see how the layouts conditionally render each `<PartyBlock>` (and the boxed wrapper around it, where a layout uses one) rather than always rendering both and hiding one with CSS.

### Line item columns (`LineItemColumns`)

`invoice.lineItemColumns` holds one entry per column — `description`, `quantity`, `rate`, `amount` — each an editable `{ label, visible }`. All four labels are renameable from the "Table columns" controls in the Line Items panel (e.g. "Description" → "Service", "Qty" → "Hours"); quantity and rate can additionally be hidden entirely, for invoices that don't need a quantity breakdown (flat-fee work) or a rate breakdown (a simple total per line). Description and amount always render — an invoice needs at least an item name and its price — so only their labels, not their visibility, are editable.

Hiding a column only changes what's *displayed*; the underlying `quantity`/`unitPrice` values on each `LineItem` are still there and still editable in the toolbar's Columns popover (dimmed and marked "(hidden)"), since `amount` is always computed from them regardless of which columns are shown.

On top of the four built-in columns, `invoice.customColumns` (`CustomColumn[]`) holds fully user-added columns — "+ Add column" in the Line Items panel appends one with an editable label, and it's removable. These are free-text and per-item (`LineItem.customValues`, keyed by the column's id): informational fields like "SKU" or "Hours", not part of the qty × rate amount math, always rendered after Amount. The shared `LineItemsTable` primitive gives custom-column cells their own `paddingLeft` directly (rather than relying on each layout's own cell classes) — Amount was always the rightmost column before this feature existed, so no layout's own styling accounted for anything following it; centralizing the spacing in the primitive means one fix covers all 19 table-based layouts instead of touching each one's className strings.

This is threaded through the same shared `LineItemsTable` primitive every table-based layout already uses (see below), so the customization applies uniformly across all of them with one change. The one layout that renders items as prose instead of a table (Timeline) doesn't consume `lineItemColumns` — there's no table to relabel — so its own "Qty"/rate wording stays fixed; this is a known, narrow gap rather than an oversight.

### Page padding (`PagePadding`)

`invoice.theme.padding` holds independent top/right/bottom/left values in px, editable from four number inputs in the Style panel. It's per-*invoice*, not per-layout, but each `TemplateDefinition` carries a `defaultPadding` that seeds it — the same pattern as `defaultAccentColor`/`defaultFont` — so a freshly-picked design starts at the spacing it was actually designed around (40–64px depending on the layout) rather than one generic number.

The padding is applied by each template's own body-content wrapper via the `paddingStyle()` helper (`src/templates/shared/padding.ts`), **not** by `InvoicePage` itself. That's deliberate: a couple of templates (Bold Gradient's header band, Corporate Blue's top accent bar) have full-bleed elements that must stay edge-to-edge regardless of this setting — if `InvoicePage` owned the padding, those bands would get pushed in from the edges along with everything else.

### Backward compatibility

Because `sections` and `theme.padding` didn't exist in early versions of the app, the store's `persist` config has a custom `merge` function that backfills both with sensible defaults for any `Invoice` already sitting in a user's `localStorage` — see the comment in `invoiceStore.ts`. Any future required field added to `Invoice` will need the same treatment, or existing users' saved invoices will rehydrate with that field `undefined` and crash the templates that read it.

`freeformLayout` went through this same treatment when it moved from a closed `Record<FreeformBlockId, {x,y,width}>` to an open `FreeformElement[]` array (see "Freeform Canvas" below) — `migrateFreeformLayout()` in `invoiceStore.ts`, exported standalone specifically so it has its own unit tests (`tests/freeformMigration.test.ts`), converts the old Record shape into the new array shape and preserves every dragged position. `merge()` runs it before `syncFreeformLayoutWithSections()` (which reconciles the array against `sections.*`), so an old save's custom layout survives both migration and the sections merge intact rather than silently resetting to defaults.

## State (`src/store/invoiceStore.ts`)

One Zustand store, one `Invoice` in it, wrapped in Zustand's `persist` middleware so it's mirrored into `localStorage` automatically on every change. This is the app's *only* persistence layer — there's no IndexedDB, no server sync. Refreshing the page restores exactly where you left off; that's the entire feature, implemented in a few lines via `persist`.

All mutations (adding a line item, editing a field, reordering, switching templates, toggling a section) go through store actions rather than components reaching into state directly — keeps the state transitions in one place and testable independent of the UI.

### Undo / redo (`src/store/history.ts`)

Every edit to the invoice is undoable — typing, moving or restyling anything on the page, adding or deleting an element, toggling a section, even switching design — from the header's Undo/Redo buttons or Ctrl/⌘+Z and Ctrl/⌘+Shift+Z (Ctrl+Y). The shortcut is deliberately taken over even while a field is focused: every field already writes straight into the store, so the document history is the real history, and the browser's own per-input undo would only fight it on a controlled input.

- **Whole-invoice snapshots, recorded in one place.** `past`/`future` hold `Invoice` snapshots. The store's actions don't call zustand's raw `set` — they call a wrapper that, whenever the action changed `invoice`, pushes the previous invoice onto `past` (and clears `future`). A new action is therefore undoable by default; it can't forget to opt in. Snapshots are cheap because every update is immutable and shares structure with its neighbor. The stack is capped at `HISTORY_LIMIT` (100).
- **Typing is one step, not one per keystroke.** `changeSignature(prev, next)` describes *what* an edit changed (`from.name`, `items:<id>.description`, `free:<id>.style.color`, `offset:to`, …). `recordEdit` folds an edit into the step already on top of the stack when it has the same signature, arrives within `COALESCE_MS` (1s) of the last one, and isn't structural. That makes typing a word, dragging a color picker, or tapping the font-size "+" repeatedly one step each. **Structural changes never merge** (adding/removing/reordering a list entry): three quick "add text" clicks are three undos. Both functions are pure, and `tests/history.test.ts` covers them.
- **History is never persisted.** `persist` uses `partialize` to save only `invoice`; without it, up to 100 snapshots (each carrying the logo's data URL) would be written to `localStorage` on every edit and quickly exhaust its quota. History therefore starts empty on each page load.
- **A new document starts a new history.** `startNewInvoice` clears both stacks rather than letting undo wander back into the invoice that was just replaced. The drag gestures only commit to the store on release (live position is local state), so a drag is a single step.
- **Selection and hover aren't part of history** — only the invoice is. After an undo, a selected element that no longer exists simply isn't selected, and the section hover outline drops itself when its section's offset no longer matches the one it was measured at.

## The template system (`src/templates/`)

This is the main extensibility point and the part most likely to see outside contributions, so it's deliberately narrow:

- **`shared/InvoiceTemplateProps.ts`** — the entire contract a template must satisfy: `{ invoice: Invoice }` in, JSX out. Nothing else is required.
- **`shared/primitives/`** — `LineItemsTable`, `Totals`, `PartyBlock`, `InvoicePage`, `Logo`, `Signature`, `EditableDate`, `Label`, `ItemText`/`FieldText`/`PartyLine`. These own the parts that must never drift between designs (the totals math wiring, currency formatting, row mapping, the two-party sign-off block) while leaving 100% of the visual styling to whichever layout uses them, via `className`/`style` props. A layout is free to *not* use a primitive and hand-roll its own markup instead — the contract doesn't require it — but in practice all of them do, which is what keeps N designs from meaning N copies of the totals logic.
- **`registry.ts`** — see "Layout × Preset" below.

See [ADDING_A_TEMPLATE.md](./ADDING_A_TEMPLATE.md) for the exact steps to contribute a design.

### Layout × Preset — how 21 components become a 105-entry catalog

The picker shows 105 selectable designs. There are not 105 hand-built React components behind it — hand-building 90+ more on top of the original 10 was never realistic while keeping each one genuinely distinct (quality collapses into near-duplicates well before 50). Instead:

- A **Layout** is one hand-built component — `ClassicTemplate`, `WatermarkTemplate`, `BlueprintTemplate`, etc. This is the expensive part: real structural design (arrangement, typography treatment, decorative elements). There are 20 of these under `src/templates/01-classic/` … `20-blueprint/`.
- A **Preset** is one `TemplateDefinition` registry entry: a Layout plus a specific `{ accentColor, font, padding }` and its own `id`/`name`/`description`. Multiple presets share one Layout `component` — nothing prevents that, `component` is just a reference. Each Layout ships with exactly 5 curated presets (colors picked deliberately per layout, never randomized), so `21 layouts × 5 presets = 105 entries`.
- `buildPresets(layoutId, layoutName, description, component, basePadding, baseFont, presets[])` in `registry.ts` generates one Layout's 5 `TemplateDefinition`s from a compact preset list, so the catalog isn't 105 hand-duplicated objects. `TEMPLATES` is the flattened concatenation of every layout's `buildPresets(...)` call.
- `TemplateDefinition.layoutId` groups presets back together — it's what `getLayoutGroups()` uses to section the picker UI ("Classic" heading with its 5 color cards under it, then "Modern Minimal," etc.) instead of showing an undifferentiated wall of 105 cards.
- **Backward compatibility constraint:** the original 10 layouts' ids (`classic`, `dark-mode`, …) are already persisted in users' `localStorage`. Each keeps its bare `layoutId` as one preset's `id` (the `suffix: 'signature'` entry in its `buildPresets(...)` call) — renaming or dropping it would break already-saved invoices. New presets on existing layouts, and all presets on the 10 newer layouts, use `${layoutId}-${suffix}` ids instead.

`createBlankInvoice()`/`createSampleInvoice()` (in `invoiceStore.ts`) look up a preset's `defaultAccentColor`/`defaultFont`/`defaultPadding` by `templateId` when a fresh invoice is created — picking from the Gallery or the drawer is the only path that resets `theme` to the preset's defaults; switching templates from the in-editor Style panel dropdown (`setTemplate`) deliberately leaves `theme` untouched, so a color/font/padding tweak survives a "let me see this in another layout" click.

Two ways to contribute, at two different effort levels — worth knowing which one fits what you want to add:

1. **A new preset of an existing layout** — cheap: add one object to that layout's `buildPresets(...)` call in `registry.ts`. No new component.
2. **A whole new layout** — the real work: a new component under `src/templates/`, then its own `buildPresets(...)` block. See [ADDING_A_TEMPLATE.md](./ADDING_A_TEMPLATE.md).

### The picker UI (`TemplatePickerGrid`, `LazyThumbnail`, `TemplatePickerDialog`)

`TemplatePickerGrid` (`src/features/template-gallery/`) is a search box plus the grouped-by-layout grid described above; it's used by both the full-page `TemplateGallery` (route `/`) and the in-editor `TemplatePickerDialog` (a large centered modal opened from the dock's *Designs* button), so the two stay visually consistent and neither reimplements search/grouping. The grid takes `layout="page" | "modal"`: the modal uses fewer, larger cards (four across on a desktop window) and a search box that stays put while the cards scroll, and marks the design the invoice is on (`currentId`, shown as a "Current" badge with `aria-current`). The picker used to be a narrow slide-in `Sheet`, which squeezed five columns of thumbnails into too little width to judge a design by; a modal gives the previews room.

At 105 cards, mounting every template's live React render simultaneously is visibly janky — each thumbnail is a real (if scaled-down) invoice render, not a static image. `LazyThumbnail` wraps the existing `TemplateThumbnail` in an `IntersectionObserver` so a card only actually renders its template once it's about to scroll into view; off-screen cards stay a lightweight skeleton placeholder. This is the one piece of infrastructure that specifically exists *because* the catalog is 100+ entries rather than 10 — worth keeping in mind if the catalog grows further.

Picking a template from either the Gallery or the drawer calls `startNewInvoice(templateId, true)` — a fresh invoice with the chosen preset's sample data, discarding whatever was in progress. This is deliberate and matches existing behavior (the Gallery page has always worked this way); it's *not* the same as the Style panel's "Design" dropdown, which quick-switches the layout on the *current* invoice without losing entered data. Two different entry points for two different intents: "start a new invoice with this look" vs. "see my current invoice in a different layout."

### Why inline `style` for color, not just Tailwind classes

Tailwind generates CSS from class names it can see *at build time*. The user's accent color is a runtime value (from a color picker), so it can never be a static Tailwind class — `bg-[${accentColor}]` will not work in a production build. Anywhere a template needs the user's accent color, it has to go through the `style` prop (see `Totals`'s `totalRowStyle`/`totalValueStyle`, `LineItemsTable`'s `headStyle`, or a plain inline `style={{ color: accent }}`). Everything else (layout, spacing, typography) uses ordinary Tailwind classes.

### Why self-hosted fonts, not a Google Fonts `<link>`

The image/PDF export rasterizes the DOM via a canvas. If a web font is still loading (or blocked) at the moment of capture, the browser silently falls back to a system font in the exported file — a bug that's easy to miss locally and easy to hit in production. Bundling fonts via `@fontsource/*` (imported in `src/index.css`) means they ship with the app and are available synchronously, no network race.

## UI components (`src/components/ui/`)

The app's chrome (the editor's toolbar popovers, buttons, dropdowns, the Designs modal) is built on [shadcn/ui](https://ui.shadcn.com/) — Radix UI primitives styled with Tailwind, installed via its CLI rather than as an npm package, so the component source lives directly in `src/components/ui/` and is meant to be read and edited like any other app code. `components.json` holds the CLI's config (style, base color, aliases); `@/` resolves to `src/` (configured in both `tsconfig.app.json`/`tsconfig.json` and `vite.config.ts`) since that's the import style shadcn's generated components use — `npx shadcn add <component>` pulls in more of them the same way.

**This is a separate concern from the invoice templates.** The 21 layouts under `src/templates/` intentionally do *not* use shadcn/Radix components — they're plain HTML/CSS driven directly by inline styles and Tailwind classes (see "Why inline `style` for color" above), because they need to be reliably rasterized by `html-to-image` and kept framework-agnostic for anyone forking a template as a starting point. shadcn is for the tool's own UI, not for what ends up on the invoice.

A few thin wrapper components sit on top of the generated shadcn primitives to keep the toolbar popovers' code from repeating itself:

- **`Field.tsx`** — a label + control wrapper. Deliberately renders a plain `<div>`, never a `<label>`: nesting an interactive `action` (e.g. `SectionToggle`'s own `<label>`-wrapped checkbox, since Radix `Label` renders a real `<label>`) inside another `<label>` makes clicking the field's title ambiguously activate whichever control the browser resolves first, instead of doing nothing (the expected behavior for a non-interactive title). Keep this in mind before "simplifying" Field back to a wrapping `<label>`.
- **`SectionToggle.tsx`** — a `Checkbox` + `Label` pairing for the "show this section on the invoice" pattern used in the toolbar's Sections popover (see `SectionVisibility` above).

Everything else in the app either uses a generated shadcn component directly (`Button`, `Input`, `Textarea`, `Select` + its sub-parts, `Popover` for the toolbar's clusters, `Dialog` for the Designs modal) or is fully custom where shadcn has no equivalent (`ZoomToFit`).

## The editor (`src/features/invoice-editor/`)

`EditorLayout` is one workspace with floating tools over it, not a frame of docked panels. A slim light **top bar** (`TopBar` — the way home, the design's name and save state, undo/redo, one **Download** menu) sits above a single dotted-paper **workspace** where `InvoicePreview` floats as a page with a soft shadow. Three things float *over* that surface and never take space from it: the **dock** (`Dock`, bottom-center — every tool), the **Elements card** (`ElementsDrawer`, top-left) and the **style pill** (`ElementStyleToolbar`, top-center — it only appears when something is selected, and restyles that; see below). Because they overlay rather than sit in the layout, opening, closing or showing any of them never reflows the page; the workspace only adds left padding while the Elements card is open so the page stays clear of it. There is no sidebar of form fields — every field that has a visual home on the invoice (business info, client info, line items, the logo) is edited by clicking it directly on the canvas (see "Click-to-edit" below); the dock only holds the handful of things that don't (invoice #/dates/currency/tax/discount, column visibility, section show/hide, design/style). `InvoicePreview` looks up the active template from the registry and renders it with the current `Invoice` — that's the entire preview implementation; there's no separate preview-specific rendering path.

**`EditorLayout` — not `InvoicePreview` — owns the `LineItemsDragProvider`/`CanvasEditProvider`/`FreeformBlockProvider` stack.** They used to live inside `InvoicePreview`, but `ElementsDrawer` and `ElementStyleToolbar` are siblings of the preview (chrome around the canvas, not inside the exported node) and need the same `FreeformBlockContext` to add elements and restyle the current selection. Lifting the providers one level up gives every consumer — preview, drawer, and toolbar alike — the same context without duplicating store wiring three times. Design-picker thumbnails never render through `EditorLayout`, so this move changes nothing about their isolation.

`ZoomToFit` (`src/components/ui/ZoomToFit.tsx`) scales the fixed-width (794px, ≈ A4 at 96dpi) preview down to fit narrower viewports using a CSS `transform: scale()` on a wrapper, while the actual template renders at full native size underneath. This matters for export correctness: the exporters grab a ref to the *unscaled* inner node, so what gets rasterized is always full resolution regardless of how small the browser window is.

### The dock (`src/features/invoice-editor/toolbar/`)

`Dock` holds every tool in one floating pill: *Designs* opens the design browser (`TemplatePickerDialog`) and *Elements*, *Uploads* and *Details* toggle the floating left card (Elements is open by default on a window wide enough to fit it beside the page, closed on a narrow one; only one of them is open at a time — they and the Business and item drawers share the one spot, `LeftPanel`), and *Draw* switches the page into draw mode. `DetailsDrawer` is the Details card: invoice #, dates, currency, tax %, discount % — settings with no single home on the page, in the left drawer rather than a popup (it reads and writes the store itself). The next three are settings with no visual home on the page, each a `Popover` anchored to a `DockButton` that opens *upward* from the dock: `ColumnsPopover` (qty/rate visibility, custom columns), `SectionsPopover` (all 7 `SectionVisibility` toggles in one place), `StylePopover` (design switcher, accent color, font, padding). `DockButton` doubles as the Radix `PopoverTrigger` (`asChild`) and takes its active look (ink-filled) from `data-state="open"`. `Popover` (not `DropdownMenu`) is the right shadcn primitive because every cluster hosts real form controls (`Input`, `Select`, `Checkbox`) inside the popup, which fights `DropdownMenu`'s roving-focus/closes-on-item-activation behavior.

**Why Download is one menu, not separate buttons.** `DownloadMenu` (a `Popover`, so it needs no extra shadcn component) lists PNG and PDF with a one-line hint each, and closes as it starts the export — outlined buttons side by side read as clutter next to undo/redo and the title, and a single primary action is where people look. The export code behind it (`handleExport` in `EditorLayout`) is unchanged.

**The look is a theme, not per-component styling — and it's the app's own.** Warm paper (`--paper`) with near-black "ink" (`--primary`/`--ink`) for primary actions, one emerald accent (`--brand`, also `--ring`) for selection and focus, a lime highlighter used once on the gallery headline, `Plus Jakarta Sans` for the interface (already bundled for the invoice font list), rounder corners (`--radius`), and soft layered shadows on everything that floats. Because they're tokens, every shadcn `Button`, focus ring and active state picks them up without being edited, and the on-page selection chrome (`FreeformBlockWrapper`, the section outline in `InvoicePreview`) reads `var(--brand)` rather than a hardcoded color. This applies to the tool's own UI only; the invoice designs under `src/templates/` deliberately don't use it (see "UI components" above). The editor was first built to mirror another editor's layout and palette closely — a gradient bar, a dark full-height rail — and was reworked specifically so it wouldn't read as a copy of one; if you restyle it, keep that in mind rather than reaching for that look again.

**Dates: click to pick, never type.** The issue and due dates on every layout open a calendar when clicked (`EditableDate`, `src/templates/shared/primitives/EditableDate.tsx`, with the calendar itself in `DatePickerCard.tsx`). It is deliberately not a native `<input type="date">` (that bakes an unfilterable calendar icon into the page and can't be styled) and not free text (an invalid ISO string would break `formatDate()`), so the stored value is always a real `YYYY-MM-DD`. The Details popover keeps its date boxes too.

`EditableDate` follows the same opt-in rule as the other primitives: with no `CanvasEditContext` (a design-picker thumbnail, an export) it returns exactly `formatDate(value)` — no wrapper, no popover — so 105 thumbnails never carry one. In the editor it is an inline `<span role="button">` that inherits the layout's text styling, with a faint hover/focus tint (`bg-current/10`, the text's own color, so it reads on dark designs). It is a `span`, not a `<button>`, on purpose: `useSectionDrag` skips presses on a `<button>` but starts a drag from anything else, so a date inside a draggable section (`meta`) can still be grabbed to move the section, while a click that doesn't move opens the calendar (a drag swallows its trailing click). The calendar is a Radix popover portaled to the document, so it is never inside the exported `#invoice-print-surface`; because React events bubble through portals, `DatePickerCard` stops pointer presses at its edge so they can't reach the page's section-drag handlers. The chosen day is filled with the invoice's accent color (`CanvasEditContext.accentColor`, since the portaled card can't inherit the page's styles) with text picked by `onAccentColor` (`lib/contrast.ts`) so a light accent stays readable. The calendar logic (six-week month grid, month-end clamping, leap years, local "today") is pure code in `lib/date.ts`, done through `Date.UTC` and never `new Date('YYYY-MM-DD')` (which is midnight UTC — the previous evening in the Americas).

## Click-to-edit (`src/templates/shared/CanvasEditContext.ts`)

Business info, client info, line items, and the logo are editable by clicking them directly on the invoice, on **every one of the 21 layouts** — not just Freeform Canvas. This works with zero changes to any individual layout file because those fields were already centralized in three shared primitives (`PartyBlock`, `LineItemsTable`, `Logo`); upgrading those three files to consume `CanvasEditContext` made every layout that already used them editable at once.

`CanvasEditContext` follows the same opt-in-via-context pattern as `LineItemsDragContext` (below), for the identical reason: these three primitives also render inside up to 105 throwaway, sample-data thumbnails in the design picker (`TemplateThumbnail.tsx`), each with its own local `createSampleInvoice()` unrelated to whatever's actually being edited. Only `InvoicePreview` (the one live, store-backed render) provides the context; every consumer calls `useCanvasEdit()` and checks for `null` before rendering an editable `InlineField` instead of static text — without that gate, clicking a thumbnail in the picker would silently edit the invoice the user is actually working on. "Only `InvoicePreview` provides it" is not enough on its own, though: the editor's Designs *dialog* is rendered inside `EditorLayout`'s providers (a portal moves the DOM, not the React tree), so a thumbnail placed there would inherit the live editor's `CanvasEditContext`, `FreeformBlockContext` and `LineItemsDragContext`. `TemplateThumbnail` therefore resets all three to `null` around its template (`tests/thumbnailIsolation.test.tsx` renders every layout's thumbnail inside live providers and asserts it has nothing clickable and nothing editable).

Because an empty optional field (address, email, phone, tax ID) must still render as a clickable, focusable input rather than nothing, `InlineField`'s `hideWhenEmptyOnExport` prop sets `data-export-hide="true"` dynamically whenever the field is empty — otherwise an untouched placeholder would bake gray "ghost" text into an exported PNG/PDF, something that could never happen on the old sidebar-only editing model.

**What the layouts' own markup does.** Each of the 20 fixed layouts' hand-rolled header text, invoice-number block and footer paragraphs are not centralized the way `PartyBlock`/`LineItemsTable`/`Logo` are — each layout composes that markup itself — so they reach the click-to-edit machinery through three small wrappers it drops in for the literal text (see "Editing text in place" below): `Label` for printed words, `FieldText` for the invoice number and footer paragraphs, `PartyLine` for a From line a layout prints in its own strip. The dates are click-to-pick (`EditableDate`). Typed in place through their own editors: party names and lines (`PartyBlock`), line-item cells and column headers (`LineItemsTable`), the Freeform Canvas's footer fields, and added Text boxes (rich text).

## Drag-and-drop

Built on `@dnd-kit`, for line-item reordering: each row is a `useSortable` item; only a small grip handle has the drag listeners attached (not the whole row), so clicking into a description/quantity/price input doesn't fight with drag detection, and `onDragEnd` resolves the old/new index and calls `reorderItems(fromIndex, toIndex)` on the store — the store, not dnd-kit, owns the actual array order.

- **`LineItemsTable`** (the shared table primitive) — reordering directly in the rendered invoice preview, so what you see is what you can grab. Opt-in via `LineItemsDragContext` (`src/templates/shared/LineItemsDragContext.ts`) for the same thumbnail-safety reason as `CanvasEditContext` above: only `InvoicePreview` provides it, so thumbnails render a plain static table with no handle and no dnd-kit wiring at all.
- The grip handle is marked `data-export-hide="true"` and both rasterized exporters (`exportToImage.ts`, `exportToPdf.ts`) pass `filter: skipExportHiddenNodes` to `html-to-image` — an editor-only affordance shouldn't end up baked into a downloaded PNG/PDF.
- Not wired into the Timeline layout, which renders items as a vertical list of its own markup rather than through `LineItemsTable` (same reason it's exempt from column customization and click-to-edit, see above) — a known, narrow gap rather than an oversight.

## Canvas behavior on every design (`InvoicePreview`, `SectionOffsetsContext`, `FreeLayer`)

All 105 designs behave like a canvas: drag any shared section anywhere on the page, and drop free-floating Text/Table/Image/Divider elements on top of the design. None of the 20 fixed layouts was rebuilt as an absolutely-positioned canvas to get this — that would erase what makes them 20 distinct, professionally composed designs. Instead the design stays as the base layer (like a template you customize) and two thin layers sit on it, both owned by `InvoicePreview` so no layout file knows about them:

**Moving sections — `SectionOffsetsContext` + `useSectionDrag`.** `invoice.sectionOffsets` (`Record<id, {x, y}>`) records how far each shared section (`logo`/`from`/`to`/`items`/`totals`/`signature`) has been dragged *from where its design places it*. Each primitive (`Logo`, `PartyBlock`, `LineItemsTable`, `Totals`, `Signature`) reads its own entry through `useMovableSection(id)` and shifts itself with a CSS `translate` on its existing root element — no wrapper div, so a layout's flex/grid arrangement around it is unchanged — and tags that root with `data-section-id`. The drag itself is `useSectionDrag`, one set of pointer handlers on the preview wrapper that finds the section under the pointer by event delegation, so all 20 layouts get it with no per-layout wiring. A section keeps its design's styling and simply moves; the gap it leaves behind stays, and it can overlap neighbors, which is the point of a canvas.

- *Click vs. drag* follows `FreeformBlockWrapper`'s rule: a press that never travels ~4px is an ordinary click and is left alone (the field focuses, the logo opens its picker); only past it does the gesture become a move, blurring whatever was focused. A field that is *already* focused is never dragged — press-and-drag inside it selects text. The click the browser fires right after a drag is swallowed, otherwise dropping the logo would open its file picker. Buttons and anything marked `data-no-section-drag` (the line-item grip, which has its own dnd-kit reorder) never start a section drag.
- *Clamped to the page.* The move is clamped so a section can't be dragged off the page, where the PNG/PDF export (which captures exactly the page) would cut it off.
- *Hover/drag outline.* `InvoicePreview` draws an outline and a label chip around the section under the pointer, as a `data-export-hide` sibling — a section's own root can't carry it, because for the line-items table that root is a `<table>` that can't hold a chrome child, and a style on the root (an `outline`) would be rasterized into the export.
- *Reset.* The drawer's "Reset positions" button (shown only when something has been moved) clears `sectionOffsets`.
- *Same thumbnail rule as every other edit context:* only `InvoicePreview` provides `SectionOffsetsContext`; thumbnails never do, so they never shift or carry `data-section-id`. `InvoicePreview` also provides `null` on Freeform Canvas, whose blocks are positioned through `freeformLayout` — a second offset on top would double-move them.
- *A layout's own markup moves too — `Movable`.* The business-name block beside the logo, the INVOICE title and number, the dates block, the notes/footer paragraphs (and a few design-specific pieces: the Postcard and Stamp & Seal stamps, Timeline's work log, Minimal Mono's headline) aren't shared primitives, so each layout tags them itself with `<Movable id="…">` (`src/templates/shared/primitives/Movable.tsx`). It's a drop-in for the element it replaces — `<div className="text-right">` becomes `<Movable id="title" className="text-right">` and renders the same tag with the same classes — rather than a wrapper `<div>`, because a wrapper would change how a hand-tuned parent flex/grid lays the element out. It composes with an element's own transform, so a tilted stamp keeps its tilt after being moved. The shared ids are `brand`, `title`, `number`, `meta`, `footer`, plus `headline`/`worklog`/`stamp`/`watermark` for the odd ones out; the full list and the labels shown on the drag outline are in `SECTION_LABELS`.
- *Decorated containers move as one piece.* Several designs put a primitive inside a bordered or tinted box (Corporate Blue's From/Bill To/table/totals boxes, Blueprint's frames, Startup/Tech's cards, Dark Mode's totals panel). Those layouts wrap the **box** in `<Movable id="to">` using the *same id* as the primitive inside it. `Movable` records its id in `MovableOwnersContext`; the primitive sees that an ancestor already owns its id and stands down — otherwise both would apply the same offset and the contents would move twice as far as their box, leaving the border behind. Pressing the label or padding of a box grabs the box; pressing inside a field still edits it.
- *Overlap, don't displace.* Every move is a CSS `translate`, so nothing reflows: the gap stays where the section was, and anything it lands on is simply painted under it. That is the intended behavior — a section should behave like a freshly added text box, free to sit anywhere on the page without pushing or replacing any other element. A section can still be moved only within the page (see *Clamped to the page* above).
- *Regression coverage.* `tests/movableSections.test.tsx` renders all 20 fixed layouts with an offset on every id and asserts that each tagged section shifts by exactly that offset, is tagged once and never nested inside another (which would move it twice), and that none of it exists without the context (the thumbnails). Add a new layout and it is picked up automatically.

- *The Watermark design's watermark is a real element* (`invoice.watermarkText` / `invoice.watermarkImage`, id `watermark`). It used to be the business name's first letter, hardcoded and untouchable. It now follows the same rules as everything else: `watermarkText` unset means "automatic" (that letter — so old invoices are unchanged), a string is the user's own text, and `''` means they removed it (the editor keeps a clickable placeholder, `data-export-hide`n so nothing exports). It's a `Movable`, so it can be moved, resized and recolored, and it's faint because of `opacity` (default `WATERMARK_DEFAULT_OPACITY`, 7%) rather than a translucent color — otherwise any color the user picked would be solid and bury the invoice. The style bar gets an opacity control for it (`FreeformElementStyle.opacity`, only offered for the watermark) and its font size auto-fits the text (`watermarkFontSize`) so "PAID" or "CONFIDENTIAL" doesn't run off the page. `InlineText` is the editable text (a `contenteditable` span that sizes to its content; an `<input>` would be a full-width box around a few letters).
- *It can be an image instead* (`watermarkImage`, a data URL resized by `resizeImageFile` on upload — PNG keeps its transparency, so a logo or stamp doesn't get a white box). While one is set it replaces the text; removing it brings the text back. An image reads as a watermark at a higher default opacity than a giant letter (`WATERMARK_IMAGE_DEFAULT_OPACITY`, 14% vs 7%), and since there's no text to recolor or embolden, `resolveStyleSelection` offers only size and opacity for it. The watermark's pill controls live in `WatermarkControls.tsx` (a text box + upload button, or a thumbnail with Replace/Remove).
- *Why a dock tool, not just clicking it.* The watermark sits *behind* the page's content, so most of it is covered by inputs and the page can only be clicked through gaps — hardly a reliable way to find it. The dock therefore shows a **Watermark** tool on that design only (selecting it), and the style pill grows a text box for the watermark's text next to the usual size/color controls. Clicking the visible part of the letter works too. Reset returns text, image *and* look to the automatic watermark through a single store action (`resetWatermark`), so it's one undo step.

**Adding elements — `FreeLayer`.** The free kinds in `invoice.freeformLayout` (`text`/`table`/`image`/`divider`) render as a click-through overlay (`pointer-events: none`, each element opts back in) on top of the template, inside the exported node, so they land in the PNG/PDF exactly where they sit on screen. They reuse the same `FreeformBlockWrapper` Freeform Canvas uses — dragging, resizing, selecting, duplicating and the style toolbar behave identically — and the wrapper grows to fit the lowest one so nothing is cropped from an export. On the fixed layouts the "bound" entries in `freeformLayout` are ignored entirely; only the free kinds are read.

**Dropping from a drawer.** `ElementsDrawer`'s cards (and `UploadsDrawer`'s, below) are draggable; `InvoicePreview` is the drop target. It converts the drop point into canvas coordinates with the wrapper's `getBoundingClientRect()` (so `ZoomToFit`'s scaling is accounted for) and passes it to `addFreeformElement(kind, at)`, which centers the element on the cursor and snaps it to the 8px grid. The drag carries a custom `dataTransfer` type (`ELEMENT_DRAG_TYPE`, or `UPLOAD_DRAG_TYPE` for an upload) so dragging selected text or a file over the page can't be mistaken for "add an element". Clicking a card still adds one at a default spot — on a fixed layout that cascades from just under a typical header (the default Freeform positions would drop it off the bottom of a shorter design); on Freeform Canvas it goes below the lowest block.

**The Business drawer.** Pressing the business name opens `BusinessDrawer` (`BusinessDrawer.tsx`) in the left card spot, one of `LeftPanel` (`'elements' | 'uploads' | 'business' | 'item'`; it has no dock button). `EditorLayout.handleSelect` wraps the selection callback it hands to `FreeformBlockContext`: pressing the `brand` block (the name and email beside the logo, present on all 20 fixed layouts) opens it, and on Freeform Canvas, which has no separate brand block, pressing the `from` block does. It is presentational — `EditorLayout` supplies the store: name and email go through `updateFrom`, the logo through `setLogo`, and the logo's look through `updateLogoStyle`, which writes `sectionStyles.logo` on a fixed layout or the Freeform logo element's `style`, exactly where the shape already lived. The look is three optional `FreeformElementStyle` fields: `shape`, `fit` (`'fill' | 'fit' | 'stretch'`, i.e. CSS `object-fit` cover / contain / fill) and `imagePosition` (nine values, CSS `object-position`); `lib/logoFit.ts` maps them, and both the drawer's preview and the `Logo` primitive use those helpers so the preview is what prints. Unset means "the whole image, centered" — what every logo did before — so existing invoices don't change. The position grid is disabled while the image is stretched, since a stretched image has nothing to position. The file-picking flow (`useLogoUpload`) and the shape buttons (`LogoShapeGroup`) are shared with the style bar's `LogoSource`.

**Editing text in place.** Clicking a piece of text on the invoice turns it into a text box right where it is — no panel, no jump. The pieces of text are `ItemText`, `Label`, `FieldText` and `PartyLine` (`src/templates/shared/primitives/`); a click turns *that very span* into a `contentEditable` box (so it keeps its font, size, color, case and position, and the cursor lands where the click did), typing calls `editText(target, text)` from `CanvasEditContext` — `EditorLayout` implements it with the store (`setLabel` / `updateField` / `updateFrom` / `updateTo`) — Enter or clicking away finishes, and Escape puts the text back (a label that never had wording of its own goes back to having none). `ItemTarget` (`src/templates/shared/ItemTarget.ts`: `label` / `field` / `party` for text, `image` / `watermark` for pictures) names what was clicked: `itemKey` is its `data-item`, `itemTitle` its accessible name while editing. One line only: Enter finishes rather than adding a line break, and paste is plain text on one line — the layouts print these as single paragraphs. Same opt-in rule as everything else: without an `editText` in the context (a thumbnail) they are exactly their children — no wrapper. Same trade-offs as `EditableDate`, deliberately: at rest an inline `<span role="button">` (so a press can still drag its section, and a click that doesn't move is what starts editing) with a hover tint only; while editing it is `data-no-section-drag` so a press inside selects text. Like `InlineText` it is **uncontrolled while you type** — it renders the text it had when editing began (a fixed string, so React never touches the DOM) and only rewrites the DOM when the value changes from somewhere else (undo/redo), or when editing ends on the value it began with (Escape). There is **no persistent "this one is being edited" highlight that could reach a file**: the hover tint and the editing ring are baked-in risks, because `html-to-image` copies *computed* styles — a label the cursor rests on when the Download menu closes would carry its tint into the PNG. `exportToImage` / `exportToPdf` run the capture inside `whileExporting` (`features/export/whileExporting.ts`), which sets `data-exporting` on the page; one rule in `index.css` (`[data-exporting] [data-item]`) turns off the background, ring and transition for that moment (the section outline is `data-export-hide`).

*Labels.* The printed words around the data are one key per role — `LabelKey` in `types/invoice.ts` (`title`, `invoiceNumber`, `issueDate`, `dueDate`, `from`, `billTo`, `subtotal`, `discount`, `tax`, `total`, `paymentTerms`, `bankDetails`, `signatureBusiness`, `signatureClient`) — stored in the optional `Invoice.labels` (no persistence migration: an invoice saved before this simply has none). A layout writes `<Label id="issueDate">Issued</Label>` with *its own wording as the child*, which is the fallback; the user's wording (`setLabel`, undoable, one step per run of typing via `changeSignature`'s `labels.<key>`) wins and is shared by every design that prints that role, so switching design keeps it. `resolveLabel` (`lib/labels.ts`) does the lookup for the page. An empty string is a real value — "print nothing" — rendered as an empty, `data-export-hide`n span that keeps a click target in the editor; `undefined` (Escape on a label that had no wording of its own) removes the override; undo gets back to each design's own words too. `LabelsContext` carries `invoice.labels` to the primitives and is provided by `InvoicePreview` only — the node every PNG/PDF export captures, so exports carry the user's wording while thumbnails always print each layout's own. A label target carries the layout's wording (`fallback`) because only the text itself knows it.

*Pictures.* Pictures are the one thing that still opens the left drawer (`ItemDrawer`, `'item'` in `LeftPanel`), via `EditorLayout.handleSelect`: the logo opens the Business drawer (which already edits it), an added Image element opens the item drawer's picture panel (Replace / Upload / Remove — `FreeformImageElement` no longer opens a file picker itself), and the Watermark design's watermark opens its picture panel (its text is an `InlineText` on the page). If the element is deleted (or undone away) while its drawer is open, the drawer closes itself.

**The logo.** A single click on the logo *selects* it; it used to open the file picker at once, which made the logo impossible to select (to move or resize) without being asked to upload something. Selecting it makes the style pill show `LogoSource` (`LogoControls.tsx`): the thumbnail with Replace / Remove (or an "Upload logo" button when there's none), a square / rounded / circle shape picker, and the usual size stepper. Double-clicking the logo still opens the picker as a shortcut. The shape is a `FreeformElementStyle.shape`, stored in `sectionStyles.logo` on the fixed layouts and on the element on Freeform Canvas; `logoRadius()` (`lib/logoShape.ts`) turns it into a corner radius, and with no shape chosen the design's own corner is kept, so existing invoices don't change.

**Uploads (`UploadsDrawer`, `store/uploadsStore.ts`).** A second left card, sharing the Elements card's spot (`EditorLayout` holds `leftPanel: 'elements' | 'uploads' | null`, so opening one closes the other). It's a personal library of images — logos, stamps, photos — kept in this browser across invoices. That's why it's its own persisted store (`invoice-generator/uploads`) and not part of the invoice: starting a new invoice must not clear it, undo must not touch it, and the images shouldn't be copied into every saved invoice. Images are downscaled with `resizeImageFile` (800px) on the way in; the library keeps the newest `MAX_UPLOADS` (24), and if `localStorage` is full the add is rolled back and the user told, rather than the library silently diverging from what's saved. A card is draggable (carrying the upload's *id*, not the image) and clickable; either way it becomes an ordinary `image` element via `addFreeformElement('image', at, { dataUrl })` (the new optional `content` argument is how an element starts with something). A card's hover actions are *Use as logo* and *Delete from uploads*; deleting never touches an invoice that already uses the image.

**Drawing (`DrawLayer`, `DrawBar`, `lib/drawing.ts`).** The dock's *Draw* tool switches the page into draw mode: `EditorLayout` holds `drawing` and the remembered `DrawSettings` (tool, color, thickness, fill), `DrawBar` replaces the style pill, and `InvoicePreview` mounts `DrawLayer`, a transparent sheet over the page that takes every press so drawing never grabs or edits what's underneath. Dragging previews the shape in the real renderer; releasing calls `addDrawing`, which stores a `drawing` element (a free kind, so it flows through `FreeLayer`/Freeform Canvas, selection, move, duplicate, delete and undo like any other). Esc or *Done* leaves the mode; a press that doesn't travel 4px draws nothing; Shift squares a rectangle/ellipse and snaps a line to 45°.

A `Drawing` is `{ tool, w, h, points, strokeWidth, fill }` in its own `0 0 w h` box: `points` are the stroke for the pencil (simplified with Ramer–Douglas–Peucker so a long scribble stores tens of points, not thousands), the two ends for line/arrow, and two corners for rectangle/ellipse. The element's `x/y/width` put that box on the page; the SVG fills the element's width and keeps its aspect ratio (elements have no height field), so resizing scales the lines too, like an image. The stroke color is the element's `style.color` and its opacity `style.opacity`, which means the existing color swatches and opacity control restyle a selected drawing with no special cases; only thickness and fill are drawing-specific (`DrawingControls`, shown in the pill when `selection.drawing` is set). `lib/drawing.ts` has no React or DOM in it: `buildDrawing` (gesture → element) and `drawingMarks` (drawing → a plain `{ tag, attrs }` list). The on-page component renders those marks as JSX.

*A drawing's box is mostly empty*, so a rectangle drawn around the totals must not stop you clicking the totals. The SVG is `pointer-events: none` and `FreeformBlockWrapper` takes `passThrough` for drawings (its own box lets presses through too); only an invisible, wider copy of the marks (`drawingHitMarks`, `data-export-hide`) is grabbable — so a 2px line is easy to pick up, an unfilled rectangle is grabbed by its outline, and a filled one anywhere. The draw layer is `data-export-hide` too, so an export never contains it.

## Freeform Canvas (`src/templates/21-freeform/`)

One of the 21 layouts, "Freeform Canvas," breaks from every other layout's fixed-flow design: every element on the page is an independently draggable, width-resizable block, and it's the one layout where *every* element — including the default business info, line items, totals, etc. — is freely positioned and width-resizable, and can be duplicated or deleted. (The drawer, free elements, and section dragging are available on all 21 layouts; see "Canvas behavior on every design" above. Freeform Canvas is the fully blank-canvas version.) It's additive — the other 20 layouts and their 100 registry entries are completely untouched by this.

**Why free-form *positioning* is a separate layout, not a mode toggle on the existing 20.** Free positioning is architecturally incompatible with how the other layouts are built (fixed Tailwind flow layout, hand-tuned per design) — retrofitting it would mean rebuilding all 100 existing entries. Freeform is additive instead: `src/templates/21-freeform/FreeformTemplate.tsx`, registered in `registry.ts` exactly like any other layout. The other 100 designs get the canvas feel from the lighter layers described above rather than from this layout: they have no coordinate system of their own, so sections move by offset and added elements float over the design.

**It reuses the same shared primitives as every other layout.** `Logo`, `PartyBlock`, `LineItemsTable`, `Totals`, `Signature` are all rendered here exactly as they are everywhere else, each wrapped in `FreeformBlockWrapper` purely for position/selection/drag chrome. There used to be Freeform-only duplicates of `PartyBlock`/`LineItemsTable` (`FreeformPartyBlock`, `FreeformItemsBlock`) — they existed only because editing was Freeform-exclusive at the time, and consuming the edit context from inside a shared primitive would have made all 100 other layouts' previews start rendering inputs too. Once click-to-edit became universal (see above), that reason disappeared, so both were retired in favor of the shared, now edit-aware primitives.

**Two contexts, not one.** Freeform's position/selection/element-CRUD state is meaningless to `PartyBlock`/`LineItemsTable`, so it's kept separate from `CanvasEditContext`:

- **`CanvasEditContext`** (`src/templates/shared/CanvasEditContext.ts`) — the universal click-to-edit context described above, consumed by `PartyBlock`/`LineItemsTable`/`Logo` on all 21 layouts.
- **`FreeformBlockContext`** (`src/templates/shared/FreeformBlockContext.ts`) — `{onMoveOrResize, selectedId, onSelect, onDelete, onDuplicate, onUpdateContent, onUpdateStyle, onAddElement}`. Consumed by `FreeformBlockWrapper.tsx` (position/selection — used by both `FreeformTemplate` and `FreeLayer`) and also by `ElementsDrawer`/`ElementStyleToolbar` (add/restyle), both siblings of the canvas rather than descendants — see "The editor" above for why the provider lives in `EditorLayout`, not `InvoicePreview`.

Both follow the same opt-in-via-context, gate-on-`null` pattern as `LineItemsDragContext` — only `InvoicePreview` provides either, so none of the 105 thumbnails can accidentally wire up pointer handlers or mutate the live invoice.

**`invoice.freeformLayout`** (`FreeformElement[]`, `src/types/invoice.ts`) is an open array of a discriminated union on `kind`, not a closed `Record`, precisely so elements can be added/duplicated/removed freely rather than being limited to 8 fixed slots. The 8 original ("bound") kinds — `logo`/`meta`/`from`/`to`/`items`/`totals`/`footer`/`signature` — carry only `{id, kind, x, y, width}`; their content still comes from the corresponding `Invoice` field, unchanged. The 4 "free" kinds — `text`/`table`/`image`/`divider` — carry their own content (`FreeformFreeContent`: `text`, `rows`, `dataUrl`, all optional) since there's no `Invoice` field backing them. Deliberately no `height` on any element, so every block's height stays content-driven/auto (see the `ResizeObserver` paragraph below).

Deleting a bound element that has a `SectionVisibility` counterpart (logo/from/to/footer/signature) is treated as equivalent to flipping that `sections.*` flag off, and vice versa — `syncFreeformLayoutWithSections()` in `invoiceStore.ts` keeps the array and the flags from silently diverging into two disagreeing sources of truth. Duplicating a bound element (e.g. "From") produces a second array entry with the same `kind: 'from'`, both bound to the same `invoice.from` — editing either updates both, intentional and consistent with how `Signature` already derives from `invoice.from.name`.

**Backward compatibility.** `freeformLayout` used to be a closed `Record<FreeformBlockId, {x,y,width}>` before the element palette existed. `migrateFreeformLayout()` (exported standalone from `invoiceStore.ts` specifically for its own unit tests, `tests/freeformMigration.test.ts`) converts an old Record-shaped save into the new array shape, preserving every dragged position rather than resetting to defaults — see "Backward compatibility" above for how it fits into the store's `merge()`.

**`ElementsDrawer`** (`src/features/invoice-editor/ElementsDrawer.tsx`) is the card `EditorLayout` floats over the workspace's top-left on every layout (Text/Table/Image/Divider rows, each with a one-line hint); it closes with its ✕ or the dock's Elements button. Drag a card onto the page to drop it where you let go, or click it to add it at a default spot (see "Canvas behavior on every design" above); it renders `null` when there's no `FreeformBlockContext` (i.e. outside the live editor). The free-kind element components live under `21-freeform/blocks/`, rendered through the shared `FreeformFreeElement` switch (a `drawing` is the fifth kind, made by drawing rather than from this card): `FreeformTextElement`, `FreeformTableElement` (an editable grid with "+ Row"/"+ Column"), `FreeformImageElement` (click-to-upload, same `resizeImageFile` path as `Logo`), `FreeformDividerElement` (a trivial `<hr>`), `FreeformDrawingElement` (an inline SVG; see "Drawing" above).

**Restyling anything on the page — `FreeformElementStyle` (`{fontSize?, scale?, color?, bold?, italic?}`, `src/types/invoice.ts`).** Click anything — a section of a design, a block on Freeform Canvas, or an element you added — and `ElementStyleToolbar` (`src/features/invoice-editor/ElementStyleToolbar.tsx`) restyles just that: size, bold, italic, color, and a Reset back to the design's own look. It is always rendered at a fixed height (with a hint when nothing is selected) rather than appearing on selection, because a bar that came and went would shove the whole page down and up on every click. Which controls apply is decided by the pure `resolveStyleSelection` (`styleSelection.ts`): an added text/table gets a real font size in px; a divider gets color only; an added image has no text so nothing; the logo gets size only; every other target gets size, bold, italic and color. A press on a section selects it (`useSectionDrag`), so the bar and a persistent selection outline (`useElementBox`, an overlay like the hover outline, never an outline on the section itself that an export would capture) follow the click.

**Why there are two kinds of size.** An added text box is plain text with no styling of its own, so `fontSize` is simply a font size. Everything built into a design is hand-styled with a different size and weight on every line (a label, a name, an address line); one px value would flatten that hierarchy. Those take `scale` instead — a multiplier on the whole block, so it keeps its proportions. It is applied as `transform: scale()` (composed after the drag `translate`, origin top-left) rather than as a font size, so growing a block never reflows its neighbors — it just overlaps them, like every other move on the canvas. On Freeform Canvas a scaled block's width resize and selection frame account for the scale, and its measured height is multiplied in so a tall scaled block can't be cropped from an export.

**Why color/bold/italic need `!important`.** The built-in sections set color and weight on every line with their own Tailwind class or an inline accent color; a value set on the block and merely inherited would lose to all of them (the reason earlier versions excluded these blocks). `styleOverride` (`templates/shared/elementStyle.ts`) instead tags the block with `data-ov-color`/`data-ov-bold`/`data-ov-italic` plus a `--ov-color` variable, and three rules at the end of `index.css` apply them with `!important` to the block **and every descendant**. `html-to-image` reads computed styles, so the Image/PDF exports carry the result. A nested block with its own override wins over an outer one, because the variable resolves from the nearest ancestor that set it.

**Coloring just some words in a Text box (`lib/richText.ts`, `RichTextField`, `richSelection.ts`).** An added Text box is rich text, so color/bold/italic go to the *words you've selected*, or to the *whole box when none are* — the style bar labels which ("Selected text" / "Whole box", at a fixed width so the controls don't shift). The box used to be a `<textarea>`, which can't hold per-word formatting; it's now a `contenteditable` (`RichTextField`) and the content is stored as restricted HTML in `element.html` next to the plain `element.text` (kept in sync; what old data falls back to — a box with no `html` just shows its `text`). `element.style` stays the whole-box baseline and per-word formatting in `html` wins over it.

- **Everything passes through `sanitizeRichHtml`.** A `contenteditable` DOM can hold almost anything (`<div>` lines, `<font>`, pasted markup), so what's stored is *rebuilt* from an allow-list — text, `<br>`, and `<span>`s carrying only a validated `color` (hex/opaque rgb → `#rrggbb`), `font-weight` and `font-style`. That keeps stored data small, makes it safe to put back into `innerHTML` (it lives in localStorage). It's pure and idempotent; `tests/richText.test.ts` covers it, including hostile input.
- **Uncontrolled while typing.** React never owns the box's contents — rewriting the DOM per keystroke would throw the caret to the start. Input is read back through the sanitizer and reported up; when the stored value changes from *outside* (undo/redo) the DOM is rewritten, detected by comparing the sanitized DOM to the stored value, so the echo of the user's own typing is a no-op. Enter inserts a `<br>` (not a `<div>`), paste is always plain text, and an empty box is `data-export-hide`n so its placeholder never exports.
- **Formatting a selection** uses `document.execCommand` (`foreColor`/`bold`/`italic`, with `styleWithCSS`). It's deprecated on paper but the only built-in that handles every nesting/overlap case (re-coloring part of a colored run, un-bolding one word of a bold phrase); a hand-rolled range wrapper gets those wrong. Pressing a toolbar button must not move focus out of the box (that drops the selection), so the toolbar cancels `mousedown` on its buttons; the native color input *must* take focus, so `richSelection.ts` remembers the last non-empty selection made in a box and restores it just before formatting (and forgets it on any press outside the toolbar and boxes, so a stale selection can't be recolored later).
- **Whole-box changes clear the per-word ones.** When the user colors the whole box, `updateFreeformElementStyle` also strips that property from every run in `html` — otherwise "make it all red" would leave the word you'd made blue, blue. It happens inside the same store update, so it's one undo step; Reset clears all per-word formatting too. (Font size is box-wide only — it isn't per-word.)
- **Dragging vs. selecting text.** `FreeformBlockWrapper` no longer starts a box drag from a press inside a field that's *already focused* (you're editing it): press-drag there selects text, as anywhere. The first press on an unfocused box still drags it (and a double-click selects a word natively). It restores the selection on release, because the page deselects on every mouse-down.

**Where each target's style is stored.** An added element (and any Freeform Canvas block) keeps it on its own `freeformLayout` entry (`updateFreeformElementStyle`). A section or design block on a fixed layout keeps it in `invoice.sectionStyles`, keyed exactly like `sectionOffsets` (`updateSectionStyle`, which drops a key patched to `undefined` and an entry left empty). `useMovableSection` reads both contexts (`SectionOffsetsContext` + `SectionStylesContext`), so anything that can be moved can be restyled, and a `Movable` wrapper that owns an id carries the style for the primitive inside it (the owner mechanism above). Like the offsets, `sectionStyles` is provided only by `InvoicePreview`, so thumbnails never pick it up. `onUpdateStyle(id, patch)` merges into the existing style so toggling bold doesn't clobber a color, and `changeSignature` names `sectionStyle:<id>.<prop>`, which is why a run of size taps is one undo step.

An *added* element (as opposed to a built-in block) takes its override as an explicit `style` *prop*, converted to CSS via `freeformStyleToCss()` (`21-freeform/blocks/freeformStyle.ts`) and passed straight to the actual text-bearing node (`InlineField`, the `<table>`, the `<hr>`'s `borderTopColor`) — not applied ambiently at `FreeformBlockWrapper` and left to cascade down. Inline `style` beats a class-based rule regardless of specificity, which is what reliably overrides `FreeformTextElement`'s own `text-sm text-slate-700` className; relying on inheritance from a wrapping ancestor would not, for the same specificity reason bound kinds are excluded above. `freeformStyleToCss()` omits any key with no value rather than emitting `fontSize: undefined` — callers spread it over their own default style object (e.g. the table's `fontSize: 13`), and an explicit `undefined` key would silently clobber that default instead of leaving it alone.

A `ResizeObserver` per block reports measured height up; since blocks are `position: absolute`, none contribute to the canvas's own height by default, so `FreeformTemplate` computes the canvas's total height as `max(1123, every block's y + measured height)` — without this, a long items list, a tall added Image, or anything positioned low on the page would paint fine on screen but get silently cropped in a PNG/PDF export (`html-to-image` sizes its capture off the node's own box).

**`InlineField`** (`src/templates/shared/primitives/InlineField.tsx`) is the borderless text control every editable canvas field uses (on Freeform and, via `PartyBlock`/`LineItemsTable`, on all 21 layouts) — a plain `<input>`/`<textarea>`, not a shadcn component, since this renders inside the exported page and needs reliable rasterization. Verified empirically (rendering one directly in the live preview, capturing it via the real `exportToImage` pipeline, and inspecting the output) that `html-to-image` correctly rasterizes typed input/textarea values, so this carries no export-fidelity risk despite being a live form control. Its `hideWhenEmptyOnExport` prop (see "Click-to-edit" above) covers empty optional fields; `FreeformImageElement`'s upload placeholder sets the equivalent `data-export-hide` by hand when `dataUrl` is null, for the same reason.

**Drag and resize** are hand-rolled pointer events (`setPointerCapture`), not `@dnd-kit` — dnd-kit's sortable primitives are built for list reordering and have no free-positioning or resize equivalent worth adopting here. Coordinate math goes through `canvasEl.getBoundingClientRect()`, not raw `movementX/Y`, because `ZoomToFit` scales the canvas via CSS `transform` on narrower windows; `getBoundingClientRect()` always reports the post-transform visual size, so `scale = rect.width / 794` is always correct with no separate state to track. Live drag/resize position lives in `FreeformTemplate`'s local `useState`, not the Zustand store — committing to the persisted store on every `pointermove` would `JSON.stringify`+`localStorage.setItem` far too often; the store is written to exactly once, on `pointerup`. Position snaps to an 8px grid live during the drag.

`FreeformBlockWrapper` disambiguates a click from a drag with a distance threshold: pointer movement stays under ~4px commits to nothing (treated as a normal click, so the child field focuses/edits normally); crossing that threshold blurs focus/clears selection and commits to a drag instead. This matters because dragging directly on a block's own text needs to move the block, not just place a text cursor — without the threshold, mousedown-on-text would always start native text selection instead.

Dates in the `meta` block stay read-only text (editable via the click-to-pick calendar, or the dock's Details drawer, like every other layout) rather than becoming an `InlineField`: a native `<input type="date">` bakes an unfilterable calendar icon into the DOM (unlike the drag handles, it's not a separate node `data-export-hide` can strip), and free-text editing would risk an invalid ISO string breaking `formatDate()`.

The footer block deliberately does *not* use `hasFooterContent()` to decide whether to render (that helper requires a section toggle on *and* non-empty content — correct for the read-only layouts, but it would create a chicken-and-egg bug here: toggle "Notes" on with nothing typed yet, and the block would never render, so there'd be no way to click into it). `FreeformTemplate` instead gates the whole block on any of the three toggles being on regardless of content; each field inside gates only on its own toggle.

## Export pipeline (`src/features/export/`)

Two independent exporters, both reading from the same `Invoice` page node:

- **`exportToImage.ts`** — `html-to-image`'s `toBlob` rasterizes the live preview DOM node at `pixelRatio: 3` (crisp on retina) and triggers a direct PNG download.
- **`exportToPdf.ts`** — same rasterization, via `toJpeg` this time, embedded into a single-page `jsPDF` document sized in mm to match the node's actual on-screen dimensions (so a 794×1123px preview becomes a ~210×297mm, i.e. A4, page).

Both capture inside `whileExporting` (see "Editing text in place") so the editor's hover and editing chrome never reaches the file.

There is no Word / DOCX export — it was removed on purpose. Both remaining exporters are a picture of exactly what is on screen, so they are faithful to every one of the 105 designs; a Word file could only approximate a design (Word can't render gradients, watermarks or free positioning), which meant a separate per-layout "style family" mapping to maintain.

Both are dynamically `import()`-ed from `EditorLayout`'s click handler rather than imported at the top of the module. `jsPDF` and `html-to-image` are large — there's no reason to make every visitor download them before they've so much as looked at a template, so they're fetched only once someone actually clicks a download button.

### Why the PDF is rasterized (not vector/selectable text)

This was a deliberate product trade-off, not a technical default. The alternative — the browser's native print-to-PDF (`window.print()` with `@media print` CSS) — produces real vector text but requires the user to go through the OS/browser print dialog and choose "Save as PDF," which breaks the one-click download pattern the other two formats have. The chosen approach captures the exact on-screen design (whichever of the 105 templates, with the user's exact color/font tweaks) and downloads it in one click, at the cost of the PDF's text not being selectable or searchable. If a future contributor wants to add the vector/print option *alongside* this one, it's a small, additive change — a print stylesheet and a second button — see the note in `exportToPdf.ts`.

### Why JPEG, not PNG, for the PDF's embedded image

Early version embedded a PNG via `pdf.addImage(dataUrl, 'PNG', ...)`, and a single invoice page came out at 20MB+ — jsPDF re-embeds PNG data close to uncompressed. The page never needs transparency (it always has an opaque background), so switching to a high-quality JPEG (`quality: 0.92`) dropped that to a few hundred KB with no visible quality loss. If you're touching `exportToPdf.ts`, keep this in mind before switching back to PNG.

## Search-engine optimization (`src/lib/site.ts`, `src/lib/seo.ts`, `vite.config.ts`)

The app is a single-page app, so search engines get a mostly empty `index.html` unless the build helps. It helps in three ways, all from one source of words:

- **`src/lib/site.ts` is the single source** of what the site says about itself: title, description, keywords, the hero text, the how-it-works steps, the features, the FAQ, the developer credit (`AUTHOR`) and the structured data (`structuredData`). The landing page (`TemplateGallery` + `LandingSections`) renders from it, and so does everything below, so the page, the snippet and the structured data cannot disagree. (`tests/seo.test.ts` checks the FAQ in the structured data is word for word the FAQ on the page.)
- **`src/lib/seo.ts` builds the pure pieces:** `buildHeadTags` (title, description, robots, icons, Open Graph and Twitter cards, JSON-LD), `buildNoscript` (the page's content as plain HTML for visitors and crawlers with no JavaScript), `buildRobotsTxt`, `buildSitemapXml`, and `escapeTag`, which escapes attribute values and the title because Vite prints tags as given. No browser or Vite APIs, so `vite.config.ts` can import it and the tests can call it.
- **The `seo` plugin in `vite.config.ts`** injects those tags and the `<noscript>` block into `index.html` (in dev as well as in the build), emits `robots.txt` and `sitemap.xml` into the build, and serves them from the dev server. `index.html` itself has only the charset, viewport and root element.

**The site's address is `VITE_SITE_URL`, read at build time (the live address is committed in `.env.production`, which Vite loads for production builds; a value set in the host's dashboard overrides it), and nothing that needs an address is written without it** — no canonical link, no `og:url`, no share-card image URLs (those must be absolute), no `url` in the structured data, no sitemap, no `Sitemap:` line. The site isn't deployed until its owner picks an address; a wrong canonical or sitemap does real harm, a missing one does none. `normalizeSiteUrl` accepts only a real http(s) address and strips the trailing slash; the build warns when it's unset.

**Per-page tags at run time** (`usePageMeta`). Everything above is the home page's, because every route shares the one HTML file. The home page and the editor each call `usePageMeta` so a crawler that runs the page (Google does) sees the right title, description and robots for the route it is on: the editor says `noindex,follow` and has no canonical link — it is a tool, not content, and the home page is what should rank. `robots.txt` deliberately does **not** disallow `/editor`: a page blocked from crawling can never show its `noindex`.

**Analytics.** `<Analytics />` (`@vercel/analytics/react`) is rendered once in `main.tsx`, outside the router's tree but inside `StrictMode`. The script follows client-side navigation, so `/` and `/editor` each count as a page view, with no query strings and no invoice data in any URL. In production it posts to Vercel's own `/_vercel/insights/*` path (inert until Analytics is enabled on the project); in development it only logs to the console. Because the site's pitch is privacy, the copy says *invoices* are never uploaded (not "nothing is") and the privacy FAQ discloses the visit counter — `tests/seo.test.ts` guards both.

**Icons and the share picture** are `public/` files: `favicon.svg`, `favicon-32.png`, `apple-touch-icon.png`, `icon-192.png`, `icon-512.png`, `og-image.png` (1200×630) and `site.webmanifest`. The PNGs were drawn with a small Python/Pillow script; to change the look, redraw them (or replace them) at the same names and sizes.

## Logo handling (`src/lib/image.ts`)

An uploaded logo (and, at 800–960px, an Uploads-library or Image-element picture) is decoded, drawn onto an offscreen `<canvas>` at a capped size (480px on the long edge for a logo), and re-encoded before it ever reaches the store. Two reasons: `localStorage` has a ~5–10MB total quota shared across the whole app, and a multi-MB phone photo used as a "logo" would both eat that quota and slow down every export. The resize happens once, at upload time, not on every render.

## Known limitations (intentional, not oversights)

- **PDF text isn't selectable** — see above.
- **Long invoices produce one very tall PDF page rather than paginating** across multiple A4 pages. Pagination would require either splitting the rasterized image across pages (visually awkward mid-row) or a from-scratch vector PDF layout per layout (a much bigger lift: a bespoke PDF layout for each of the 21 layouts). Not attempted for v1.
